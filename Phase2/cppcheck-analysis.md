# Running Cppcheck

## Objective

Run Cppcheck on the BIRD v2.17.1 source code to identify potential bugs, coding issues, style problems, performance improvements, portability concerns, and other static analysis findings.

---

## Output Directory

A dedicated directory was created to store the generated report.

```bash
mkdir -p reports/cppcheck
```

---

# Running Cppcheck

Command:

```bash
cppcheck \
  --enable=all \
  --inconclusive \
  --force \
  --xml \
  --xml-version=2 \
  . 2> reports/cppcheck/cppcheck-result.xml
```

## Command Options

| Option | Description |
|---------|-------------|
| `--enable=all` | Enables all available checks, including warnings, style, performance, portability, information, and unused code analysis. |
| `--inconclusive` | Reports potential issues with lower confidence that may require manual verification. |
| `--force` | Forces analysis of all configurations and source files. |
| `--xml` | Generates the output in XML format. |
| `--xml-version=2` | Produces XML using version 2 of the Cppcheck output schema. |

---

# Result

The analysis completed successfully.

Generated report:

```
reports/cppcheck/cppcheck-result.xml
```

The XML report contains all findings generated by Cppcheck and will be used later for:

- Manual review of reported issues.
- Importing external issues into SonarQube.

---
## Using Compilation Context

### Objective

To reduce analysis noise and false positives, Cppcheck was re-executed using the project's compilation database. Instead of analyzing the source code without build information, Cppcheck was provided with the actual compiler commands, include paths, and compiler options generated during the BIRD build process.

The compilation database (`compile_commands.json`) was generated using **Bear** while rebuilding the project.

---

## Generating the Compilation Database

```bash
bear -- make -j1
```

This command generated the following file:

```text
compile_commands.json
```

The compilation database contains the actual compilation commands used by GCC, including:

- Source files
- Include directories
- Compiler flags
- Preprocessor definitions

Providing this information allows Cppcheck to analyze the project using the same compilation context as the real build.

---

## Running Cppcheck with Compilation Context

### Command

```bash
cppcheck \
  --project=compile_commands.json \
  --enable=all \
  --inconclusive \
  -j1 \
  --xml \
  --xml-version=2 \
  2> reports/cppcheck/context.xml
```

### Command Options

| Option | Description |
|---------|-------------|
| `--project=compile_commands.json` | Uses the compilation database generated by Bear. |
| `--enable=all` | Enables all available Cppcheck checks. |
| `--inconclusive` | Reports lower-confidence findings that may require manual verification. |
| `-j1` | Runs the analysis using a single thread to produce deterministic results. |
| `--xml` | Generates XML output. |
| `--xml-version=2` | Uses version 2 of the XML output format. |

### Result

The analysis completed successfully.

Generated report:

```text
reports/cppcheck/context.xml
```

---

## Running a Security-Focused Analysis

After evaluating the context-aware analysis, a second scan was performed using a reduced set of checks to minimize informational and style-related findings while keeping warnings that are more relevant for security analysis.

### Command

```bash
cppcheck \
  --project=compile_commands.json \
  --enable=warning,performance,portability \
  --inconclusive \
  -j1 \
  --xml \
  --xml-version=2 \
  2> reports/cppcheck/cppcheck-final.xml
```

### Result

The analysis completed successfully.

Generated report:

```text
reports/cppcheck/cppcheck-final.xml
```

A second, security-focused configuration further reduced analysis noise by excluding informational and style-related findings, producing a report better suited for manual review and integration into SonarQube as external issues.

# Cppcheck Scope Filtering Analysis


The purpose of this analysis was to compare different approaches for restricting
Cppcheck analysis to the main BIRD source directories and to evaluate their
effect on the number of reported findings.

---

## Allowed Source Scope

The intended analysis scope was:

```text
client/
conf/
filter/
lib/
nest/
proto/
sysdep/
```

The following directories were intended to be excluded:
```text
obj/
test/
tests/
doc/
tools/
distro/
misc/
```
## 1. Normal Cppcheck Analysis

The initial analysis used the complete compilation database:
```bash
cppcheck \
  --project=compile_commands.json \
  --enable=warning,performance,portability \
  --inconclusive \
  -j1 \
  --xml \
  --xml-version=2 \
  2> reports/cppcheck/cppcheck-final.xml
```
Output:
```text
reports/cppcheck/cppcheck-final.xml
```
Result:
```text
119 findings
```

## 2. Filtering the Compilation Database

A filtered compilation database was created using jq:
```bash
jq '
  map(
    select(
      (.file | contains("/client/")) or
      (.file | contains("/conf/")) or
      (.file | contains("/filter/")) or
      (.file | contains("/lib/")) or
      (.file | contains("/nest/")) or
      (.file | contains("/proto/")) or
      (.file | contains("/sysdep/"))
    )
  )
' compile_commands.json > compile_commands-analysis.json
```
Cppcheck was then executed using the filtered database:
```bash
cppcheck \
  --project=compile_commands-analysis.json \
  --enable=warning,performance,portability \
  --inconclusive \
  -j1 \
  --xml \
  --xml-version=2 \
  2> reports/cppcheck/cppcheck-final-scoped.xml
```
Output:
```text
reports/cppcheck/cppcheck-final-scoped.xml
```
Result:
```text
113 findings
```
Compared with the normal analysis, 6 findings were removed.

The removed findings were associated with the following files:
```text
conf/cf-lex.l
filter/decl.m4
proto/ospf/config.Y
```
Specifically:

Rule 	 |File    	|Line(s)  |
|------|---------:|--------:|
allocaCalled	|conf/cf-lex.l|	486, 487|
nullPointerArithmeticRedundantCheck	|conf/cf-lex.l|	196, 197, 233, 234|
syntaxError	|filter/decl.m4|	837|
unknownMacro|	proto/ospf/config.Y	|97

These files are located under the intended source directories, but they are
associated with BIRD's source-generation/build process rather than being
ordinary compiled C/C++ translation units.

## 3. Cppcheck --file-filter

Cppcheck also provides a native file filtering mechanism.

The original compilation database was kept unchanged and the analysis scope was
specified directly using --file-filter:
```bash
cppcheck \
  --project=compile_commands.json \
  --file-filter='client/*' \
  --file-filter='conf/*' \
  --file-filter='filter/*' \
  --file-filter='lib/*' \
  --file-filter='nest/*' \
  --file-filter='proto/*' \
  --file-filter='sysdep/*' \
  --enable=warning,performance,portability \
  --inconclusive \
  -j1 \
  --xml \
  --xml-version=2 \
  2> reports/cppcheck/cppcheck-file-filter.xml
```
Output:
```text
reports/cppcheck/cppcheck-file-filter.xml
```
Result:
```text
113 findings
```
The same 6 findings were removed as in the filtered compilation database
approach.

## 4. Comparison

Analysis Method |Findings|
|------|--------:|
Normal compile_commands.json	|119
Filtered compile_commands-analysis.json	|113
--file-filter	|113

Both filtering approaches removed the same findings associated with:
```text
conf/cf-lex.l
filter/decl.m4
proto/ospf/config.Y
```
No additional findings were introduced by either filtering method.

## 5. Conclusion

Both approaches successfully restricted the Cppcheck analysis to the intended
source scope.

For this project, both methods produced the same result:
```text
Normal analysis       : 119 findings
Filtered analysis     : 113 findings
Difference             : 6 findings
```
The native --file-filter approach was preferred for the final analysis because
it keeps the original compile_commands.json unchanged and applies the scope
directly within Cppcheck.

Final output:
```text
reports/cppcheck/cppcheck-file-filter.xml
```
Final result:
```text
113 findings
```
